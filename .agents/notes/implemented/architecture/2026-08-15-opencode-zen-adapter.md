# Agent Note: OpenCode Zen free-model LLM adapter

Status: implemented

English | [中文](2026-08-15-opencode-zen-adapter.zh.md)

## Problem

deepseek-harness ships two `LlmAdapter` providers: `dsh-llm-deepseek` (direct OpenAI-compatible fetch for the `deepseek-official` route) and `dsh-llm-pi-ai` (a library-backed catalog of providers). Neither exposes OpenCode Zen — the keyless free-model gateway that powers opencode.ai's anonymous tier (`https://opencode.ai/zen/v1`, literal bearer `public`) — as a first-class route.

OpenCode Zen is reachable through pi-ai's `openai-completions` hand-declared route today, but only with friction: pi-ai's compatible implementation requires an API key or `Authorization` header (a placeholder credential or header entry), the model catalog must be hand-written, and there is no tokenless default. The anonymous free tier's defining property is that no credential exists anywhere; a config-only wire-up cannot express that default, and no curated free-model catalog is shipped. The integration we wanted — "call opencodeai's free models directly from deepseek-harness" — needs a provider that authenticates anonymous by default and advertises the free catalog out of the box.

## Decision

Add a new adapter package [`@deepseek-ai/dsh-llm-opencode-zen`](../../../../packages/llm/llm-opencode-zen/README.md) (leaf `packages/llm/llm-opencode-zen`) owning the single provider route `opencode-zen`. It is a direct-fetch, OpenAI-compatible chat-completions adapter shaped after the DeepSeek twin: `LlmRuntime` registration, per-operation config thunk, settings/credentials layering, an idle watchdog, and the harness `attributionHeaders()` (see [twin LLM adapters](2026-06-13-twin-llm-adapters.md)).

The adapter's defining difference is authentication: omitting `apiKeyEnv` resolves the request bearer to the literal `public` — the anonymous free tier — so a composition needs no key, no credentials seam, and no environment variable to run free models. A configured `apiKeyEnv` resolves per request through `ctx.credentials` then the process environment, and a reference that resolves to nothing fails with `MISSING_CREDENTIAL` rather than downgrading a deployment that explicitly asked for a real key. The `models` default is the curated free-tier catalog served by `https://opencode.ai/zen/v1/models` (`deepseek-v4-flash-free`, `mimo-v2.5-free`, `hy3-free`, `nemotron-3-ultra-free`, `nemotron-3.5-lightning-free`, `laguna-s-2.1-free`); the list stays advisory like the DeepSeek twin's.

Reasoning effort is deliberately unsupported: the free catalog spans providers with mutually incompatible effort vocabularies, so the adapter sends no `reasoning_effort`, advertises no `reasoning` capability, and refuses an explicit `GenerateOptions.reasoningEffort` with `UNSUPPORTED_REASONING_EFFORT` before I/O. A deployment needing a specific dialect uses the pi-ai `openai-completions` route.

Error classification adds the anonymous tier's per-IP quota: a 429 whose provider `type` is `FreeUsageLimitError` or `GoUsageLimitError` classifies as `QUOTA_EXCEEDED`, keeping request throttling at `RATE_LIMIT`.

Every request mints OpenCode Zen's session-scoped identity headers (`x-opencode-session: ses_<hex>`, `x-opencode-request: msg_<hex>`, `x-opencode-project: <hex>`, `x-opencode-client: dsh`), byte-shape matching the official opencode CLI. Live capture of the CLI's wire request and A/B probing established that the anonymous free tier keys quota on these session ids rather than the raw source IP: bare anonymous requests (no identity headers) drained the shared per-IP bucket and then failed with 429 for hours, while fresh well-formed `ses_*` ids kept succeeding. Minting a fresh id set per request is therefore what makes the harness behave like the official client instead of exhausting a shared IP pool.

The gateway additionally 429-limits the POPULAR free models (`deepseek-v4-flash-free`, `mimo-v2.5-free`) for requests it does not recognize as opencode-ecosystem clients. A/B probing pinned the discriminator to the `User-Agent`: the official-prefixed `opencode/local ai-sdk/provider-utils/4.0.23 runtime/bun/1.4.0 (deepseek-harness)` passes with any `x-opencode-client`, while the attribution default (or a bare PowerShell UA) fails. The adapter therefore replaces the `attributionHeaders()` default `User-Agent` with that official-prefixed client string — a white-label replacement the attribution contract allows, never a suppression — keeping the `(deepseek-harness)` suffix so the wire stays honestly labeled. A stored `opencode` API key from the user's opencode auth.json does NOT unlock these models (verified: still 429); the client User-Agent is the operative factor. The wire modules (`parseSse`, `translate`, the OpenAI message serializer, wire types) intentionally twin `dsh-llm-deepseek` byte-for-byte minus the thinking/effort fields; the shared-transport extraction the DeepSeek adapter's `TODO(http)` anticipates is the deferred refactor this duplication awaits, and `jscpd:ignore` markers bound the allowed surface (the same sanctioned mechanism as every package's `invariant.ts`).

The shipped verification exercised the non-trivial gate set expected of a product-visible plugin: per-file 100% coverage on every `src` file (types excluded), a real Loader+Include composition booting `llm + settings-file + credentials-local + llm-opencode-zen` from `cordis.yml` (anonymous default and authenticated external-edit rotation), HMR route disposal, retry-policy replace without an empty-registry window, and a bilingual README pair with a recorded consistency file.

## Alternatives considered

- **Extract a shared OpenAI-compatible transport package used by both adapters.** The correct long-term home, and the one the duplicated `jscpd` surface argues for, but it would refactor the shipped `dsh-llm-deepseek` package, halve the duplication into a new first consumer before a second exists ("require a current owner and need"), and re-open the twin-adapters blast radius. Deferred: the existing `TODO(http)` thread and this note name it.
- **Config-only via `dsh-llm-pi-ai`'s `openai-completions` route.** Zero code, but no tokenless default (pi-ai's compatible implementation requires a key or `Authorization` header), no shipped free catalog, no `FreeUsageLimitError`/`QUOTA` mapping, and no discoverable `opencode-zen` route in the models page. Kept as the documented escape hatch for a deployment that needs a dialect field this adapter refuses.
- **Vendor `@opencode-ai/llm` from the opencodeai repository.** That client is Effect-based, in-repo-only (not on npm), and expresses a different vocabulary than the harness `StreamChunk` contract; it also carries none of the anonymous-bearer gating, which lives in the CLI and the hosted gateway, not the client. The harness's own `LlmAdapter` contract is the integration seam.

## Consequences

The free tier is best-effort and shared: anonymous quota is session-scoped (minted per request) yet intermittently limited — exhaustion surfaces as HTTP 429 `FreeUsageLimitError` (`QUOTA_EXCEEDED`), and some free models answer a class of prompts with an empty stream. Availability is not guaranteed, so the integration treats it as a roll-your-own-availability tier rather than a stable SLA. No reasoning-effort control crosses the wire, which narrows the adapter's surface but also means a free model that could be forced to think harder gets only its provider default. The allowed wire duplication adds a maintenance constraint: the twin modules and their `jscpd:ignore` blocks must stay in sync with `dsh-llm-deepseek` until the shared transport lands. The `examples/headless-agent` composition still uses the DeepSeek route; an OpenCode Zen agent is a settings-document or composition change (`provider: opencode-zen`, `model: deepseek-v4-flash-free`, no key).
